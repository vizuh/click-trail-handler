### Findings

- **F1, #152 cache leak reproduced for Contact Form 7 (run 1; fixed on main, see the rerun table).** Visitor B's cookie held `fbclid=BFB`, `utm_source=b_src` and no
  `gclid`; the page HTML was visitor A's (`gclid=AAA`). B's CF7 posted data and B's stored lead carried
  `ct_gclid`, `ct_ft_gclid`, `ct_lt_gclid` = `AAA` next to B's own `BFB` and `b_src`. The rendered `ct_*` inputs still held
  A's values when B submitted (the browser runtime only overwrites keys B's cookie has). Cause: `cookie_value_for()` returns
  `null` for a key the cookie lacks (`includes/integrations/forms/class-abstract-form-adapter.php:292`) and
  `CF7_Adapter::refresh_posted_data()` then keeps the posted value (`includes/integrations/forms/class-cf7-adapter.php:98`),
  which is the intentional "keys the cookie lacks keep the posted value" rule that a cached page turns into someone else's
  value. Fluent Forms and WPForms did not leak in this harness. Fluent's cached HTML did carry A's values, in the inputs
  ClickTrail echoes at `form_element_start` (`ct_ft_gclid=AAA`, `ct_lt_gclid=AAA` were in B's DOM), but those are not builder
  fields and Fluent drops them before the entry; the builder `ct_*` fields held no A value at submit. WPForms Lite renders
  nothing for these fields, so its cached HTML carried no A value. A WPForms Pro hidden field is filled at render (`render_field_default()`), so the
  leak there is plausible but was not run.
- **F2, WPForms Lite cannot render the documented hidden field.** In Lite 2.0.3.1 the `hidden` type is a Pro field
  (`wp-content/plugins/wpforms-lite/src/Forms/Fields/Hidden/Field.php`, `ProField` trait, `field_display()` is empty): a form
  that contains one renders no input (DOM `ct_*` map was `{}`). `WPForms_Adapter::render_field_default()` only handles
  `type === 'hidden'` (`includes/integrations/forms/class-wpforms-adapter.php:94`) so nothing is filled at render on Lite.
  The server-side `wpforms_process_filter` refresh does not check the type, so a `ct_<key>` field of any type (here a
  Single Line Text field with the CSS classes `ct_<key> wpforms-field-hidden`) and even the unrendered hidden-type field get
  the cookie value at submit. Both variants are in the run (`wpforms_text`, `wpforms_hidden`). This answers the open question
  in `specs/004-submit-time-refresh-parity/research.md`.
- **F3, WPForms Lite keeps no entries.** `wpforms()->entry_meta` is unset and `entry_id` is 0, so `entry_meta` writes
  (`WPForms_Adapter::on_submission()`) cannot happen and could not be asserted; the processed field values at
  `wpforms_process_complete` and ClickTrail's own log row were.
- **F4, plugin PHP warning on every front-end page view while consent is required and not granted.**
  `Events_Logger::render_server_events()` runs on `wp_head` at priority 5 (`includes/Modules/Events/class-events-logger.php:53`)
  and calls `clear_event_cookie()` for three cookie names (`:173`) whose `setcookie()` (`:152`) is after output started:
  `PHP Warning: Cannot modify header information - headers already sent by (output started at
  wp-includes/template-canvas.php:13)`. 13 occurrences, matching the page views of the run where consent was not (yet)
  granted (8 deny/ignore contexts, 4 pre-accept loads, 1 optimizer page dump). PHP rejects the header, so the cookie clear
  cannot take effect. [INFERENCE] a site with `display_errors` on would print the warning into the page head. The
  success-path clear at `:187` is the same call from the same hook; it was not triggered here (no `ct_event_*` cookie).
- **F5, deprecation notice per Fluent Forms submission.** Fluent Forms 6.2.16 raises `PHP Deprecated: Hook
  fluentform_insert_response_data is deprecated since version 4.3.22! Use fluentform/insert_response_data instead.` whenever a
  callback is attached to the legacy name. `Fluent_Forms_Adapter::register_hooks()` attaches one
  (`includes/integrations/forms/class-fluent-forms-adapter.php:56`) next to the slash-style hook (`:51`). 7 notices for 7
  Fluent submissions; the line is attributed to WordPress core, not to the plugin path, so a path-based scan misses it.
  `verify_adapters.py` matches it by message. The legacy `form_element_start` and `submission_inserted` aliases (`:55`, `:57`)
  raised no notice.
- **Observation, not a defect:** with `WP_DEBUG` on, 120 `ClickTrail: consent override by caller "unknown"` lines were logged
  (`includes/tracking/class-consent-decision.php:34`): callers pass `marketing_allowed` without a `caller`.

## How each scenario is asserted

- **Stored lead**: `wp_clicutcl_events` rows of type `form_submission` created during the scenario (`event_data.attribution`),
  and the matching dispatch captured at `capture.invalid`.
- **Provider entry**: Fluent Forms `fluentform_submissions.response` and `fluentform_submission_meta`; CF7 posted data at
  `wpcf7_mail_sent` and WPForms processed fields at `wpforms_process_complete`, both recorded by the read-only
  `mu/ct-e2e-provider-capture.php` (priority 99), because neither plugin stores entries by default in this setup.
- **Fixtures**: the CF7 form from `setup.sh`; a Fluent form with native hidden fields `ct_gclid`, `ct_fbclid`, `ct_ft_source`,
  `ct_lt_source`, `ct_lt_medium`, `ct_attribution_selected_click_id` (the documented configuration); two WPForms forms with the
  same six fields, one `hidden` type, one Single Line Text, both marked by CSS class `ct_<key>`.

## 2026-11-02: edge-cache headers on UTM / click-ID landing pages (#164, scenario S8 `edge_cache_headers`)

Question: does ClickTrail make a public landing page uncacheable for a CDN (`Set-Cookie`, `Cache-Control` changes, `Vary: Cookie`)?

**Measured** (WordPress 7.1 + Apache/PHP 8.3 in the harness pod, plugin mounted, raw `http.client` GET/GET/HEAD, no browser, no redirects).
Pages: `/landing/?gclid=X&utm_source=t`, `/?gclid=X&utm_source=t` (plain page), `/form-cf7/?gclid=X&utm_source=t` (CF7 form).
States: consent required + no consent cookie (first-time visitor), consent granted cookie, consent denied cookie, consent not required, and a request
carrying a stale `ct_event_login` cookie (not a first visit). Every request was repeated with the plugin deactivated (`wp plugin deactivate click-trail-handler`) as baseline;
`verify_adapters.py` asserts HTTP 200, no `Set-Cookie`, `Cache-Control` / `Expires` / `Pragma` / `Vary` / `ETag` / `Last-Modified` identical to the baseline, no `Vary: Cookie`, no `no-cache`. 132 PASS in the full run.

**Defect found and fixed**: against `main` @ 805a721 every anonymous page view with consent required and not granted answered with three `Set-Cookie` headers
(`ct_event_login=deleted`, `ct_event_signup=deleted`, `ct_event_comment=deleted`), GET and HEAD, all three pages. `Events_Logger::process_event_cookies()` (`send_headers`)
expired the three follow-up cookies unconditionally; Cloudflare and other CDNs do not cache a response that sets a cookie. Baseline (plugin off) sends none. S8 failed on that code, passes with the fix
(expire only cookies the request carries); `EventsLoggerCookieHeadersTest` covers it. A request that does carry `ct_event_login` still gets exactly that one expiry (asserted, expected).

**Source audit** (`includes/`, grep `nocache_headers|DONOTCACHEPAGE|no-cache|setcookie|header(`):
- `nocache_headers()`: only `includes/admin/class-gtm-lead-magnet.php:341`, an admin download handler; cannot fire on front-end pages. No `DONOTCACHEPAGE`, no `no-cache` string, no `Cache-Control` / `Vary` header written anywhere in `includes/`.
- `setcookie(` on front-end hooks: `class-events-logger.php:139` (`set_event_cookie`, from `wp_login` / `user_register` / `comment_post`, POST or login flows, consent-gated), `:160` (`clear_event_cookie`, the defect above, now only for a cookie present on the request); `class-clicutcl-core.php:494` and `:518` (`clicutcl_admin_qa`, set on `init` only for logged-in users with `manage_options`, cleared on `wp_logout`; logged-in responses are not edge-cached).
- The attribution cookie is client-side only (`clicutcl-attribution.js`); no PHP writes it. (Superseded by #141 below: `Attribution_Cookie_Reissue` sets it, on the REST route `POST /clicutcl/v2/cookie-refresh` only.)

**Not measured**: any real CDN, Cloudflare, `cf-cache-status`, or page-cache plugin (a header comparison on the origin only); the staging site; HTTPS (`Secure` flag path); logged-in requests; `/wp-json` responses.
Evidence wording: runtime-verified in the local harness for origin response headers; edge-cache behaviour itself stays unverified.

## 2026-11-02: attribution cookie restore and server re-issue (#141, `specs/009-itp-cookie-reissue/`, `tools/qa/e2e/cookie-reissue.sh`)

Question: does the server re-issue set the same cookie on the wire, only on the REST `POST`, with the lifetime and domain the script uses, and does the browser end with one cookie?

**Measured** (WordPress + Apache/PHP 8.3 in the harness pod, plugin mounted, Chromium via Playwright 1.59.0, one site served as `www.example.test` and `example.test` over http): 49 checks, 0 failures.
- Page `GET`/`HEAD` of `/landing/?gclid=X&utm_source=t` and `/?gclid=X`, with no cookie, with a valid `attribution` cookie and with `attribution` + a granted `ct_consent`: no `Set-Cookie` in any response, and none on the three page documents of the browser runs. `adapters-ci.sh` S8 `edge_cache_headers`: 132 PASS on the same code (316 PASS, 6 FINDING (WPForms Lite has no entry API), 0 FAIL overall); `ci.sh`: 0 failures.
- Raw `POST /wp-json/clicutcl/v2/cookie-refresh` with the page's client token and an `attribution` cookie: 200, exactly one `Set-Cookie: attribution=<value, encodeURIComponent form>; Max-Age=7776000; Path=/; Domain=example.test; SameSite=Lax` (`cookie_days` 90, scope `registrable`), `Cache-Control: no-store, private`, no `HttpOnly`, no `Secure` (http). Same on the apex host. No cookie, legacy name only, invalid JSON, a nested value and an oversized value: 200 `reissued:false`, no header. Missing or wrong token: 401. `GET`: 404. Consent required: no consent cookie 403, denied 403, granted 200 with the header. Setting off: 403 `cookie_reissue_disabled` and an empty `cookieReissueUrl` in the page config.
- Browser (every script write of `attribution` capped to 24 hours by an init script to emulate Safari): the landing sends one `POST` (the response is observed in `mu/ct-e2e-set-cookie-log.php`, because Chromium reports no response for a `keepalive` fetch), the jar ends with exactly one `attribution` cookie (domain `.example.test` under `registrable`, `www.example.test` under `host`, not `HttpOnly`, `SameSite=Lax`) whose expiry is 90 days from the request (0 s off), so the server's cookie replaced the capped script cookie; the marker is cleared; a second page view sends nothing. After dropping only the cookie, the next page restores it from the localStorage mirror (one cookie, same domain attribute) and one more re-issue follows. Control with the setting off: the cookie stays capped at 24 hours, the restore still happens, no request. Consent required and undecided: no request, no cookie, no `attribution` or marker key in localStorage; after consent is granted, a cookie and one request. A request answered 429 (my own rerun inside the one-minute rate-limit window) left the capped script cookie and the marker in place, as designed.

**Not measured**: Safari or iOS (the 24-hour cap is emulated, not WebKit), https (`Secure` is covered by `AttributionCookieReissueTest` only), a real CDN or page cache in front of the REST route, a cache that stores `POST` responses, consent kept only in `localStorage` by a third-party CMP.
Evidence wording: runtime-verified in the local harness for the wire shape and the Chromium cookie jar; Safari behaviour stays runtime-unverified.
