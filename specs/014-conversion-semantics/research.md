## Vendor facts (read 2026-11-09)

- **W1** WooCommerce paid statuses. `wc_get_is_paid_statuses()` returns `apply_filters( 'woocommerce_order_is_paid_statuses', array( processing, completed ) )` (`plugins/woocommerce/includes/wc-order-functions.php:135-143`, `trunk`).
- **W2** `payment_complete()` sets the date paid (when unset) and the status (`processing` if the order needs processing, else `completed`, filter `woocommerce_payment_complete_order_status`), saves, then fires `woocommerce_payment_complete` (`includes/class-wc-order.php:147-297`, `trunk`). `status_transition()` fires `woocommerce_order_status_<to>` and `woocommerce_order_status_changed` on save (`:613-658`). So for a normal gateway payment both hooks run, the status hook first.
- **W3** Offline gateways. "Offline - No online payment is made. Example: Cheque, Bank Transfer." The Cheque example sets `on-hold` ("we're awaiting the cheque") and returns the thank-you redirect; "If payment is complete, let WooCommerce handle the status and use `$order->payment_complete()`" ([Payment Gateway API](https://developer.woocommerce.com/docs/features/payments/payment-gateway-api)). "If the provider accepted the payment and will confirm it later, set the order to On-Hold and send the shopper to the order received page" (same page, "Retries and uncertain outcomes").
- **W4** COD. `WC_Gateway_COD::process_payment()` sets `apply_filters( 'woocommerce_cod_process_payment_order_status', $order->has_downloadable_item() ? on-hold : processing, $order )` with the note "Payment to be made upon delivery." (`includes/gateways/cod/class-wc-gateway-cod.php:126-139`, `trunk`). `processing` is a paid status (W1), so COD counts as paid at checkout.
- **W5** Thank-you template. `templates/checkout/thankyou.php` prints the failed notice when the order has status `failed`, else the overview, then fires `woocommerce_thankyou_<method>` and `woocommerce_thankyou` after that block (lines 28-97, `trunk`). The hook therefore fires for failed orders.
- **W6** Block order confirmation. None of the files in `src/Blocks/BlockTypes/OrderConfirmation/` read on `trunk` contains `do_action( 'woocommerce_thankyou'`; `Status.php` only applies `woocommerce_thankyou_order_received_*` filters. Whether the hook fires on a block-theme order-received page is `unverified`; the harness must request the page in both the shortcode and the block template.
- **W7** `created_via`. Classic checkout `set_created_via( 'checkout' )` (`includes/class-wc-checkout.php:546`); Store API `set_created_via( 'store-api' )` (`src/StoreApi/Utilities/OrderController.php:67`), `trunk`. The REST v3 documentation describes the field as "Shows where the order was created. It can only be set during order creation".
- **W8** WooCommerce Subscriptions core. `wcs_create_order_from_subscription()` creates renewal and resubscribe orders with `'created_via' => 'subscription'` (`includes/wcs-order-functions.php:232`, `Automattic/woocommerce-subscriptions-core` `trunk`); `wcs_order_contains_subscription( $order, $order_type )` accepts `parent`, `renewal`, `resubscribe`, `switch`, `any` (`:402`). Not in the harness: runtime-unverified.

The only `do_action( 'edd_update_payment_status' )` located in `class-edd-payment.php` is the `refunded` branch (`:2067`); the emission point for completion was not located, so it is `unverified` until run on EDD 3.7.3. If you only want to run your action for the initial purchase (and ignore subscription renewals) you will need to check the `$order->status` for a value of `complete`"; `edd_complete_purchase` "runs during the purchase process ... before the 'Purchase Confirmation' page is loaded" ([After order actions](https://easydigitaldownloads.com/docs/adding-custom-code-after-an-order-is-completed/)).

Orders left in Pending payment are no longer tracked by default" ([What GTM4WP 2.0 changes](https://gtm4wp.com/development-log/what-gtm4wp-2-0-changes-for-woocommerce-stores.html), 2026-08-27). ## R1: Two settings, one card

**Decision**: `purchase_trigger` (`thankyou` | `paid`) for ecommerce and `thank_you_lead` (`always` | `fallback` | `never`) for lead gen, both in `clicutcl_attribution_settings`, one admin card, both with the cookie-scope pattern (schema default is the legacy value, the activation seed writes the new value on fresh installs only).
**Rationale**: the two problems are different. A purchase has an objective paid state; a lead has none, and the only evidence a page visit follows a submit is session evidence. One enum (`legacy` | `strict`) would silently drop thank-you leads for new installs whose forms have no adapter, which is what the owner asked to be an explicit opt-in. `purchase_trigger` is named for what it decides and sits beside `cookie_scope`, `attribution_cookie_reissue`, `woo_enhanced_datalayer`.
**Rejected**: one `conversion_semantics` enum (above); storing the Woo setting in `clicutcl_gtm` next to `woo_enhanced_datalayer` (the activation seed, `Attribution_Settings::get_all()` and the server paths read the attribution option; two options would need two seeds); per-matcher flags in the `clicutcl_thank_you_matchers` array (filter-only, no UI, and it cannot express the existing-install default).

## R2: The step event

**Decision**: `ct_thank_you_view`; payload in FR-004; pushed in every mode and install; dataLayer only, no server copy in v1; no value, currency, items or PII; deduped per tab session and per order or path.
**Rationale**: a new name cannot break an existing container. `ct_` follows `ct_page_view`, the only existing event that ClickTrail namespaces so a catch-all tag cannot confuse it with a vendor event. No `ecommerce` object, so a GA4 or Ads tag that reads `ecommerce.value` cannot treat the step as revenue. A server copy would reach the collector as an unmapped event name (the adapters post the whole event and tag it, `class-meta-capi-adapter.php:58-82`; what the downstream collector does with it is outside ClickTrail), and the browser route would reject it unless it were added to `BROWSER_EVENT_NAMES`.
**Alternatives**: `thank_you_view` (plain, matches `lead` and `purchase`; but the prefix signals "ClickTrail step, not a vendor name"); `order_received` (ecommerce vocabulary, wrong for leads); `confirmation_view`; a `ct_` page-view variant with a `thank_you` flag on `ct_page_view` (changes an existing event). **Hugo decision needed**: final name.
**Catch-all triggers**: a GTM trigger or GA4 Event tag that matches every custom event (the starter kit's notes already warn about this for `ct_page_view`, `docs/architecture/EVENT-PIPELINE.md:74`) will start seeing one more event; that is the only compatibility effect.

## R3: What "paid" means

**Decision**: `wc_get_is_paid_statuses()` (W1) passed through a ClickTrail filter `clicutcl_woocommerce_paid_statuses`; EDD keeps its three-status list.
**Rationale**: it is WooCommerce's own definition, already used by the `order_paid` milestone (`class-woocommerce.php:389`), it respects the merchant's `woocommerce_order_is_paid_statuses` customisation, and it makes the plugin agree with `$order->is_paid()`.
**Alternatives**: (a) a ClickTrail status multiselect like GTM4WP's (default Processing, On hold, Completed; W10): rejected, because counting `on-hold` is the behaviour the owner called wrong (a bank transfer is not money paid) and a UI list duplicates a Woo filter; (b) `$order->get_date_paid()` as the signal: rejected, because merchants set the paid date through gateways inconsistently and a status gate is what GA4 and Ads reconcile against; (c) `payment_complete` hook only: rejected, because offline gateways and administrators move orders with `update_status()` and never call it.

## R4: Server `purchase` at the paid transition, shared marker, channels

**Decision**: dispatch from the same two hooks the milestone uses (`woocommerce_payment_complete`, status into a paid status), with `event_id = purchase_<order_id>`, under `Claim_Lock( 'clicutcl_purchase_lock_<id>' )`, marker `_clicutcl_tracking_sent` with values `server`, `browser`, `yes`.
**Rationale**: the owner asked for the same `purchase_<id>`, the same marker, the same lock and the same queue key so the paths cannot both count. That is four layers: marker (long-lived, survives erase and retention), `Claim_Lock` (concurrency, 30 s), `Dedup_Store` (transient, 7 days default, not atomic) and `UNIQUE (event_name, event_id)` in the queue. A single marker for two channels is not enough on its own: at card payment the server dispatch runs inside the checkout request (W2), before the thank-you page, so a plain truthy marker would make the thank-you page return early and the browser `purchase` (which GTM tags depend on) would never be pushed. The marker therefore records which channels are done. It keeps the retention-exempt key the privacy code already manages, adding no key, no `EXACT_META_KEYS` entry and no uninstall change; the extra values are `server` and `browser`, and legacy `yes` still means both.
**Alternatives**: a second meta key for the browser channel (needs entries in `Woo_Order_Privacy::EXACT_META_KEYS`, the retention exemption and the uninstall path, `:40-47`, and is one more thing to keep in step); browser dedupe by `sessionStorage` only (a reload on another device pushes again); reuse `maybe_dispatch_order_milestone()` (writes the wrong marker, `:721`, has no lock and no retention guard); fire the server copy only from the thank-you page (the status quo, loses buyers who never return, which the owner wants covered).
**Consequence**: with delivery disabled the server channel does not mark (milestone semantics, FR-007e), so the two hooks retry cheaply on later status changes; the touch-event row is unique by event key and is not duplicated.

## R5: COD and offline statuses

**Decision**: follow WooCommerce (W1, W4): a COD order is `processing` at checkout and counts as paid; a bank-transfer or cheque order is `on-hold` and does not. Document the caveat in the setting help; offer the filter, not a setting.
**Rationale**: the only per-gateway rule ClickTrail could add would be a gateway id list, which is a second definition of "paid" to maintain. Merchants who want cash-collected-only already have `woocommerce_order_is_paid_statuses`.
**Alternatives**: exclude `cod` by payment method (a special case on a gateway id; wrong for merchants who consider COD a sale); count `on-hold` by default as GTM4WP does (W10; rejected by the owner's model). **Hugo decision needed**: COD handling (follow Woo, or exclude COD until `completed`).

## R6: Consent for a purchase sent after the visitor left

**Decision**: precedence as `Dispatcher::consent_allows()` has it, plus one rule: outside a customer request the cookie is ignored and only the order's checkout snapshot decides; identity follows the snapshot.
**Source-read findings**: (1) the milestone path decides consent through `Dispatcher::consent_allows()`: live cookie authoritative when present, else the snapshot carried on the payload (`:420-440`); `dispatch_order_payload()` also pre-checks `Consent::is_required() && Consent::has_state() && ! marketing_allowed()` (`class-woocommerce.php:648`). (2) When an administrator changes the status in wp-admin and has a ClickTrail consent cookie of their own, that cookie is "present" and decides: a denial skips the buyer's event, a grant sends it even if the buyer's stored snapshot is a denial (the payload carries the denied snapshot, but the gate returns `marketing_allowed()` of the administrator before it looks at it). The bank-transfer flow is exactly an administrator action, so `paid` makes this reachable for `purchase`; `order_paid` already has it. (3) `resolve_purchase_identity()` passes live `Consent::marketing_allowed()` (`:1131`); in a webhook, cron or WP-CLI request with no cookie and consent required that is false even when the snapshot granted, so the hashed identity is withheld from a server `purchase` that the dispatcher will send. (4) The queue never trusts a cookie; on consent-required sites a retried event waits on `clicutcl_queue_consent_snapshot`, whose default is null (`class-queue.php:282-306`), so a queued `purchase` stays `consent_unresolved` unless a site supplies the filter.
**Decision detail**: carry `meta.consent_authority = order_snapshot` for non-customer requests and honour it in the dispatcher; resolve identity from the snapshot in the same case. Applies to `purchase`; extending it to `order_paid`, `order_refunded` and `order_cancelled` is a behaviour change to released milestones. **Hugo decision needed**: include the milestones (recommended: same code path, same hazard) or leave them.
**Limit**: later withdrawal by the buyer is not visible to a request without their cookie; the stored grant stands (same limit as spec 013 R8 and spec 008 R10). **Hugo decision needed**: whether a per-order withdrawal record is wanted (not in v1).

## R7: Retention

**Decision**: the server channel refuses by creation date; the thank-you channel keeps paid-date-first.
**Rationale**: retention removes `_clicutcl_consent` and the attribution by `date_created` (`class-woo-order-privacy.php:369-380`). A bank transfer created long ago and paid today has no snapshot left: on a consent-required site the dispatcher fails closed, on a site that does not require consent it would send a `purchase` with no attribution and no consent record. The thank-you rule exists for buyers who pay an old order and arrive with live consent (`class-woocommerce.php:309-310`); that is a browser event under live consent and stays.
**Alternative**: one shared guard (paid date first): rejected for the server path for the reason above.

## R8: Which orders are purchases

**Decision**: allowlist `created_via` in (`checkout`, `store-api`) plus filter `clicutcl_woocommerce_purchase_created_via`.
**Rationale**: the paid server hook now fires for every order that becomes paid, including orders the legacy thank-you path never saw: automatic Subscriptions renewals (`created_via = subscription`, W8), administrator and REST orders, imports. Those are not shopper checkouts and have no attribution to carry. Orders created through ClickTrail's own save hooks are exactly the checkout and Store API ones (`class-woocommerce.php:62-63`).
**Alternatives**: (a) denylist (`subscription`, `admin`, `rest-api`): over-counts every integration that creates orders with its own `created_via` (POS, marketplaces, importers) and fails open; (b) presence of `_clicutcl_consent` (written for every ClickTrail-seen checkout): precise, but it disappears at retention and for orders created before the plugin was installed, and the rule would be invisible to operators; (c) `wcs_order_contains_subscription()` (needs Subscriptions loaded and covers renewals only). Cost of the allowlist: a gateway that creates orders with its own `created_via` loses its `purchase` (still gets `order_paid`) until the filter lists it. **Hugo decision needed**: should an administrator-created order that the customer pays through a payment link count as a purchase (the allowlist says no)?

## R9: Pending-then-paid browser recovery (Phase 2)

**Decision**: not in v1. v1 covers the never-returning buyer through the server `purchase` and the returning buyer who reloads the thank-you URL (the page re-evaluates the paid state on every load, so a reload after payment pushes the browser `purchase` once).
**Phase 2 option**: remember on the server that an order is awaiting a browser push (order meta or a short-lived option keyed to the visitor and session, written only after consent) and push `purchase` on the next page the same browser views once the order is paid; the GTM4WP "Reliable purchase tracking" (W10) is the precedent, experimental and off by default there, and its documentation states it cannot recover a buyer who never returns. The design questions for Phase 2: the key that ties the browser to the order without a cookie before consent, the maximum waiting time, and cache-safe delivery (a full-page cache serves the same HTML to everyone, so the push needs a REST or fragment read).
**Rejected for v1**: it adds a store, a reader on every page view and a consent surface for a case the server `purchase` already covers when delivery is configured. **Hugo decision needed**: ship it, and when.

## R10: Lead gen

**Decision**: step event on matched pages; the lead stays at submit time; `thank_you_lead` decides whether the page also pushes a `lead`.
**Evidence for `fallback`**: in-page dedupe is memory-only (`markOnce`, `:2307`), so a `lead` pushed on the form page is invisible to the thank-you page after a redirect or a full reload. The only cross-page evidence the browser can hold is session storage written at submit time. Two markers: `ct_lead_seen` (a ClickTrail-confirmed `lead` or `lead_submit` push, strong) and `ct_form_submit_seen` (the `submit` listener already runs for every form, `:844`, and is the only thing that sees a server-only adapter's submit, for example WPForms or Gravity Forms with a redirect confirmation, where no browser `lead` exists).
**Limits**: `ct_form_submit_seen` is written for any form in the tab, so a search or newsletter form earlier in the session suppresses the fallback lead; that is the price of not reading any form content. A window or a form-id match could narrow it. **Hugo decision needed**: accept session-wide submit evidence (v1 proposal), narrow it (time window, same form), or accept adapter-confirmed evidence only (misses server-only adapters).
**Alternatives**: (a) `thank_you_lead` as a boolean (cannot express "only when no adapter lead"); (b) read the server `form_submission` log on the thank-you page (a request per page view and a cache problem); (c) a short-lived cookie set by the PHP adapter on the POST (a `Set-Cookie` and a consent surface that the product avoids on page views, #164); (d) matcher entries that carry a form id (no UI, filter-only today). **Hugo decision needed**: names `thank_you_lead` / `always|fallback|never`.
**Legacy**: `always` is byte-identical to today for the `lead`; whether to retire it later is a separate decision (open question 3).
**Order-received pages in the matcher list**: a site that lists its Woo order-received path in `clicutcl_thank_you_matchers` would get `lead_thank_you` from the script and `order_confirmation` from PHP; the Woo config gets an `orderReceived` flag (`build_woocommerce_events_config()`, `class-clicutcl-core.php:568-` has `pageType` values `product`, `cart`, `checkout`, `other` only) and the script defers.

## R11: Defaults and migration

**Decision**: existing installs `thankyou` / `always`; fresh installs `paid` / `never`, written once by `seed_fresh_install_defaults()` under its earlier-use guard; no upgrade routine writes them; changing the default for existing installs is not planned for 1.x (open question 2).
**Rationale**: reported revenue must not change on update. The cookie-scope precedent shows the machinery works and is tested (`tests/unit/CookieScopeSettingsTest.php`, spec 007 FR-002).
**Starter kit**: the kit's thank-you page conversion (`Google Ads - Thank You Conversion` on the page-view trigger) is the customer's GTM page-view logic and keeps working unchanged; it is the lead-gen equivalent of the problem this spec names. The kit can gain an event trigger on `ct_thank_you_view` (additive) and a note; retargeting the existing tag is a decision for Hugo. Side finding, already tracked as spec 012 Q5: the kit's `LC - form_submit` trigger listens for `form_submit`, a name no ClickTrail script or PHP path pushes (grep of `assets/js` and `includes` found none).

## R12: EDD

**Decision**: same setting; `thankyou` keeps today's paid-gated receipt; `paid` adds the server dispatch on transition into a complete status, the shared marker values and the step event on the receipt.
**Rationale**: EDD does not have the failed-or-pending thank-you problem (the receipt push is gated, `class-edd.php:118`); its gap is the opposite: an offsite gateway whose receipt is visited while the order is still pending counts nothing until the buyer returns, and a buyer who never returns is lost. The hook is EDD's own completion hook (W9) but its emission for non-refund statuses is unverified.
**Renewals**: Recurring Payments renewals use the `edd_subscription` status (W9), outside `PAID_STATUSES`; Software Licensing renewals bought at checkout are ordinary `complete` sales and count (unverified, not in the harness).
